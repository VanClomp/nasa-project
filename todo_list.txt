The Szukacz is implemented in the 4-szukacz/ folder. Full description of the input
and output: 4-szukacz/README.md. Below are the things that need changes or
decisions in other modules. The Szukacz did not change any file outside its own

NETWORKER and FRONTEND (POST /search request)
---------------------------------------------

1. New input field: min_distance_km (number >= 0).
   Minimum distance in km between the returned locations. Of two points lying
   closer together the Szukacz takes only the better one, and still returns top_k
   results. The Szukacz assumes it receives this value in the request.
   - To do: the Frontend collects the value from the user (or fixes a constant),
     the Networker forwards it unchanged to http://szukacz:8002/search.
   - While the field is missing from the request, the Szukacz uses 100 km
     (the SZUKACZ_MIN_DISTANCE_KM variable). The value 0 turns the filtering off.

2. The other request fields are unchanged: features_norm, weights,
   require_caves, top_k.


NETWORKER and FRONTEND (POST /search response)
----------------------------------------------

3. No name_hint field.
   The Szukacz does not return a region name. explorer.php puts c.name_hint into the
   candidate card (around line 791) and will show "undefined".
   - To do: the frontend shows something else (e.g. coordinates) or another
     module adds the name.

4. Extra candidate field: features_norm.
   The point's 9 normalised features in its best month. The frontend already
   uses it when re-scoring the sliders live. Nothing to do, just a note that the
   field is outside the spec.

5. heatmap_base64 is a ready-made texture.
   "data:image/webp;base64,...", an RGBA 1024x512 image, colour #10B981, opacity
   grows with the match, pixels without data are transparent. The opacity scale is
   relative to the query (best point = fully opaque).
   - To do: the frontend currently draws its own heatmap from blobs around the
     candidates (explorer.php, around line 536) and does not read this field. To
     show the real map, this image has to be laid over the Earth globe.

6. Months are counted from 1 (best_month, best_global_month: 1..12).
   monthly_scores and the arrays in climatogram_12m have 12 entries, index 0 is
   January. Consistent with how explorer.php reads them.

7. Edge cases the frontend should handle:
   - candidates can have fewer than top_k entries or be empty
     (e.g. require_caves with no caves nearby); then best_global_month = null.
   - Missing data in the matrices comes out as null (in monthly_scores,
     features_raw_best_month, climatogram_12m, nearest_cave_km).
   - An invalid request gives status 422 with a description in the "detail" field.
     Note: callApi in explorer.php silently switches to the built-in PHP mock on
     any status other than 200, so the error will not be visible.

8. climatogram_12m contains all 9 features, not just temp_mean
   and soil_moisture. The response for 100 candidates is about 270 kB plus a
   heatmap of about 110 kB (measured on synthetic data).

9. The require_caves filter uses a 15 km threshold (the same value as in the mock
   in explorer.php). Change it with the SZUKACZ_CAVE_MAX_KM variable.


PRECOMPUTER (files in /data/earth)
----------------------------------

10. The Szukacz reads exactly what section 4.1 of the spec describes:
    - earth_features_norm.npy  (N_POINTS, 12, 9) float32, values [0, 1]
    - earth_features_raw.npy   the same shape, physical values
    - earth_metadata.parquet or earth_metadata.npy (structured array)
      with the columns: id, lat, lon, px_x (0..1023), px_y (0..511),
      nearest_cave_km. Rows in the same order as the matrices.
    With a different shape or a missing column the service will not start
    and will print what is missing.

11. Missing data: ideally the matrices contain no NaN. If they do,
    a month with NaN in any feature (even one with weight 0) loses
    to the others, and a point without a single complete month is left out of the results.

ERROR MAP (added 2026-11-14, full description in 4-szukacz/README.md)
---------------------------------------------------------------------

The error is the weighted difference between the target profile and the features of a place on Earth
(a number from 0 to 1, error = 1 - score). The Szukacz now returns it as a map
of the whole Earth and, on request, as a detailed map of the area around a point.

17. New field in the POST /search response: error_map.
    An object with the fields image_base64, width, height, bounds, scale, stats.
    - Networker: nothing to do. /api/v1/search passes the Szukacz response through
      whole, so the field goes through. This follows from the code of
      2-networker/networker/api.py; it was not checked on a running
      cluster.
    - Frontend: to do, if the map should be visible. image_base64 is
      "data:image/png;base64,..." (PNG, not WebP like the heatmap), a
      1024x512 image laid over the Earth globe in the same way as heatmap_base64.
      A transparent pixel = no data. The legend is drawn from the scale field:
      9 colours spread evenly from scale.min (0) to scale.max (0.5),
      dark = small error, bright = large. The scale is fixed for all
      queries, unlike in the heatmap.
    - The /search response grew by 90-130 kB (mock data, 60,000
      and 400,000 points).
    - The end of the colour scale is set by the SZUKACZ_ERROR_SCALE_MAX variable
      (default 0.5). Without changes to docker-compose.yml the default
      value is used.

18. New Szukacz endpoint: POST /error-map (detailed map around a point).
    Request: features_norm and weights (the same as in /search), lat, lon,
    optionally radius_km (1..2000, default 250) and size_px (64..1024,
    default 512). Response: execution_time_ms, center, radius_km,
    km_per_px, error_map (the same format as in item 17).
    - Networker: to do. A public route is needed, e.g.
      POST /api/v1/error-map, that forwards the request unchanged to
      http://szukacz:8002/error-map and returns the response and status 422
      unchanged. Until it exists, the frontend has no access to the map.
      [Update 2026-11-15] Done: 2-networker/networker/api.py has POST /api/v1/error-map.
    - Frontend: to do. Call it after choosing a candidate or clicking
      the Earth globe, with the same features_norm and weights as the last
      /search. Where the image lies is given by error_map.bounds (degrees).

19. Cases the frontend should handle in the map from item 18:
    - bounds.lon_min and lon_max go beyond [-180, 180] when the window crosses
      the 180th meridian (e.g. 170..190).
    - height is smaller than size_px when the window reaches a pole.
    - An area without data (ocean) gives a fully transparent image,
      and in stats: n_points = 0 and null in min, mean and max.
    - Response time: about 27 ms with the default values, up to about 160 ms
      with radius_km = 2000 and size_px = 1024 (400,000 points).

20. PRECOMPUTER: the detail of the map from item 18 depends on the point density.
    The map does not interpolate: a pixel shows the error of the nearest data point.
    The 60,000-point mock has about 1.4 points per pixel of the 1024x512 grid, so
    the map shows little more than the whole-Earth map; the gain appears
    only with denser data (400,000 points is about 3.7 per pixel).
    The Szukacz assumes points spread evenly in degrees (a regular
    lat/lon grid). If the target grid is different, e.g.
    equal-area, gaps between points will appear in the map near the poles
    and the fill rule will need adjusting.
    [Update 2026-11-15] The real Earth data is a regular 0.2 deg lat/lon grid
    (551,832 land points), as assumed here.
